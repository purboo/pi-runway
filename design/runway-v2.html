pi-runway 0.2 信息全画在输入框的上下边框上 · footer 一行都不占 · 按键零计算

借 topping 的点子：信息嵌进输入框的上下边框，footer 不再单独占行；context 用量画成一格一格的色块，放在下边框右端。但做法不同：颜色连续渐变，不按档位跳；多一段“虚影”标出下一轮预计用量；按键时不做任何计算。

上边框：左边是“在哪”（目录、分支、其他扩展的状态），右边是模型和 thinking。下边框：左边是运行计时（只在运行中出现，紧挨光标），右边是费用和 context 表。pi 原本放在边框中间的“↑/↓ N more”滚动提示照常保留。

② 表的构成

每格的颜色由它在表上的位置决定：越往右越热。所以光看最右边那格的颜色，就知道离满还有多远，不用读数字。没填的格子用同样的形状、很暗的颜色，不用 topping 那种 ░ 网点，看着更干净。

③ 八种状态 · 120 列

平时只有一条安静的表。70% 起数字变黄并给出剩余轮数，90% 变红。压缩时整条表有一道光扫过。

④ 配色：选一套

四套都只用主题里本来就有的颜色，然后在 OKLab 空间里插值，保证渐变均匀不发脏。终端不支持真彩色时自动退回到最近的分档颜色。

⑤ 窄终端 · 运行中

两条边框各自让位：上边框依次收起 thinking、状态、完整路径、分支、模型；下边框依次收起费用增量、计时、色块格数，最后只留百分比。

⑥ 为什么快

打字卡的根源是渲染时做计算。pi 每按一次键都会重绘输入框和 footer。所以规则只有一条：render() 里不算任何东西，只拼接已经算好的字符串。

每次按键调用 getContextUsage() → 重算整个 session（buildSessionProjection），session 越长越慢返回缓存的字符串；只有宽度或数据变了才重新拼，O(1)
context 用量每次渲染都重算运行中直接读 message_end 带的 usage；只在 agent_end、压缩、换模型、载入 session 时调一次 getContextUsage()
费用—每条消息到来时累加；只在载入 session 或切换分支时整体扫一遍
git定时起进程跑 git status（约 0.18 s / 20 s）分支名用 pi 自带的监听；脏标记只在 write / edit / bash 工具结束后查一次，带防抖
定时器max thinking 时彩虹边框持续动画（约 14 秒一圈），另有状态滑入动画只在运行中每秒跳一次（计时变了才重绘）；只在压缩期间跑扫光动画
输入框整个编辑器重新包一层盒子，加左右边、宽度缩 6 列只替换编辑器的 renderTopBorder() / renderBottomBorder()：不缩宽度、不加侧边、不碰按键处理，footer 返回 0 行。别的扩展换掉了编辑器、没有这两个方法时，自动退回成 footer 一行
验收标准测试里造一个 10,000 条记录的 session，连续渲染 1,000 次总耗时 < 5 ms

⑦ 需要你拍板

  1. 位置：全部放在输入框边框（推荐，省一行）、只把表放边框（footer 留一行），还是全放 footer（完全不碰编辑器）？
  2. 配色：aurora / green / mono / tinted 选一套。我倾向 aurora：空闲时也好看，越热越红的意思也清楚。tinted 跟着 thinking 等级变色，但 xhigh、max 本身就是粉红色，会被看成报警。
  3. 下一轮虚影：一直显示，还是只在 70% 以上显示？
  4. 窗口大小：数字写成 41% 还是 41%/1M？
  5. 按 token 数提前变色：topping 在 1M 窗口下用到 15 万 token 就开始变色，理由是 context 越长模型越容易“走神”。这一条对不同模型并不一样，我建议不做，只看百分比。
